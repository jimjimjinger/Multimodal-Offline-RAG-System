# 상황 인지형 멀티모달 RAG 시스템 전체 설명서

## 1. 이 문서의 목적

이 문서는 현재 프로젝트의 전체 구조를 처음 보는 사람도 이해할 수 있도록 풀어서 설명한 문서이다. 논문 초안은 연구 배경과 실험 결과 중심으로 작성되어 있지만, 이 문서는 시스템이 실제로 어떻게 동작하는지, 텍스트와 이미지가 어떤 방식으로 연결되는지, 질문이 들어왔을 때 어떤 과정을 거쳐 답변과 이미지를 함께 제공하는지를 자세히 설명한다.

핵심 질문은 다음과 같다.

- 이 시스템은 무엇을 하는가?
- 매뉴얼의 텍스트와 이미지는 어떻게 추출되는가?
- 텍스트와 이미지는 어떤 방식으로 서로 연결되는가?
- 사용자가 질문하면 어떤 검색 과정이 일어나는가?
- G1, G2, G3, G4는 각각 무엇이 다른가?
- G4의 상황 인지형 검색은 무엇을 추가한 것인가?
- 로컬 LLM은 어떤 역할을 하고, 이미지는 어떤 방식으로 함께 제공되는가?
- 왜 이 시스템을 오프라인 및 저사양 환경 지향 시스템이라고 볼 수 있는가?
- 현재 시스템의 강점과 한계는 무엇인가?

## 2. 한 문장으로 설명하면

이 시스템은 협동 로봇 실습 매뉴얼에서 텍스트 설명과 이미지/도식 자료를 함께 검색하고, 사용자의 질문에 맞는 매뉴얼 근거와 관련 이미지를 찾아 로컬 LLM이 한국어 실습 안내 답변을 생성하도록 만든 오프라인 멀티모달 RAG 시스템이다.

여기서 오프라인이라는 말은 사용자가 질문할 때 외부 API나 클라우드 LLM을 호출하지 않고, 로컬에 저장된 매뉴얼 데이터베이스와 로컬 LLM을 사용한다는 뜻이다. 또한 이 시스템은 고성능 서버가 아니라 8GB RAM급 노트북까지 고려한 제한 자원형 구동을 목표로 설계되었다. 그래서 SigLIP처럼 무거운 모델은 앱 실행 중 매번 돌리지 않고 전처리 단계에서만 사용하며, 앱에서는 이미 만들어진 ChromaDB 인덱스와 양자화된 로컬 LLM을 중심으로 동작하도록 구성한다.

더 쉽게 말하면, 사용자가 다음과 같이 묻는다고 가정한다.

> 로봇 베이스를 바닥에 고정할 때 사용하는 볼트와 토크는 얼마입니까?

일반 검색 시스템은 관련 문장만 찾아준다. 하지만 협동 로봇 실습에서는 문장만으로 부족할 수 있다. 볼트 위치나 고정 방법을 보여주는 그림도 필요하다. 이 시스템은 다음 두 가지를 동시에 하려고 한다.

1. 질문에 답할 수 있는 매뉴얼 텍스트를 찾는다.
2. 그 텍스트와 관련된 이미지/도식도 함께 찾는다.

그리고 최종적으로 앱 화면에는 다음이 함께 나온다.

- 로컬 LLM의 한국어 답변
- 답변에 사용된 Top-5 매뉴얼 텍스트 근거
- 관련 이미지/도식 Top-10

## 3. 이 시스템이 필요한 이유

협동 로봇 실습 매뉴얼은 단순한 글 문서가 아니다. 설치, 전원 연결, 티치 펜던트 조작, 안전 설정, I/O 배선, 좌표계 설정 등은 텍스트 설명과 이미지 자료가 함께 있어야 이해하기 쉽다.

예를 들어 다음과 같은 질문은 텍스트와 이미지가 모두 중요하다.

| 질문 유형 | 텍스트로 필요한 정보 | 이미지로 필요한 정보 |
|---|---|---|
| 설치 절차 | 볼트 규격, 토크, 주의사항 | 베이스 고정 위치 도면 |
| 전원/접지 | 접지 조건, 누전차단기 조건 | 컨트롤러 연결부 이미지 |
| 티치 펜던트 조작 | 메뉴 경로, 버튼명 | 실제 화면 위치 |
| I/O 배선 | 단자 이름, 신호 조건 | 배선도 |
| 안전 설정 | 제한 구역, 충돌 민감도 설명 | 안전 설정 화면 |

텍스트 기반 RAG만 사용하면 문장 답변은 어느 정도 가능하지만, “어떤 그림을 같이 봐야 하는지”를 잘 찾지 못한다. 그래서 본 프로젝트는 텍스트와 이미지를 연결하는 멀티모달 검색 구조를 만든다.

## 4. 전체 시스템 흐름

전체 구조는 크게 네 단계로 나눌 수 있다.

```text
1. 오프라인 전처리
   매뉴얼 PDF에서 텍스트와 이미지를 추출하고 정리

2. 인덱싱
   텍스트와 이미지 관련 정보를 임베딩하여 ChromaDB에 저장

3. 런타임 검색
   사용자의 질문에 대해 관련 텍스트와 이미지를 검색

4. 답변 생성 및 표시
   검색된 텍스트를 로컬 LLM에 넣어 답변을 만들고, 관련 이미지를 함께 표시
```

조금 더 구체적으로 쓰면 다음과 같다.

```text
협동 로봇 매뉴얼 PDF
        |
        v
텍스트 추출 + 이미지/도식 추출
        |
        +-- 텍스트 chunk 생성
        +-- 이미지 파일 저장
        +-- 이미지 page, bbox, SigLIP score 저장
        |
        v
텍스트-이미지 매핑 생성
        |
        +-- 같은 page 또는 인접 page인지 확인
        +-- 텍스트 bbox와 이미지 bbox 거리 계산
        +-- SigLIP image-text similarity 계산
        |
        v
ChromaDB 인덱싱
        |
        +-- 텍스트 collection
        +-- 이미지 collection
        |
        v
사용자 질문 입력
        |
        +-- BGE-M3로 질문 임베딩
        +-- 관련 텍스트 Top-5 검색
        +-- 관련 이미지 Top-10 검색
        +-- G4에서는 실습 단계 추정 후 re-ranking
        |
        v
Ollama 로컬 LLM 답변 생성
        |
        v
답변 + 근거 텍스트 + 이미지 표시
```

## 6. 사용한 모델과 역할

이 시스템에는 여러 모델이 들어가지만, 각 모델의 역할은 다르다.

| 모델/도구 | 사용 시점 | 역할 |
|---|---|---|
| BGE-M3 | 전처리, 검색, 단계 분류 | 질문과 텍스트의 의미 유사도 계산 |
| SigLIP | 전처리 | 이미지가 도식인지 판별하고 텍스트-이미지 유사도 신호 계산 |
| ChromaDB | 전처리 후 저장, 런타임 검색 | 텍스트와 이미지 검색 인덱스 저장 |
| Ollama | 런타임 | Qwen/Gemma/Llama 로컬 LLM 실행 |
| Qwen/Gemma/Llama | 런타임 | 검색된 근거를 바탕으로 한국어 답변 생성 |

중요한 점은 LLM이 이미지를 직접 보고 해석하는 구조가 아니라는 것이다. 현재 시스템에서 이미지는 다음 방식으로 활용된다.

1. 전처리 단계에서 이미지가 어느 page에 있고 어떤 텍스트 주변에 있는지 기록한다.
2. 이미지와 관련된 주변 텍스트를 이용해 이미지 검색용 문서를 만든다.
3. 질문이 들어오면 그 이미지 문서도 검색한다.
4. 검색된 이미지 파일을 앱 화면에 함께 보여준다.

즉, LLM은 주로 텍스트 근거를 읽고 답변을 생성한다. 이미지는 답변의 시각적 근거로 같이 표시된다.

### 6.1 오프라인 및 저사양 환경 지향 설계

이 프로젝트의 중요한 강점 중 하나는 클라우드 기반 서비스가 아니라 로컬 환경에서 동작하도록 설계했다는 점이다. 협동 로봇 실습실이나 교육 현장에서는 인터넷 연결이 불안정하거나, 외부 API 사용이 제한되거나, 실습 매뉴얼과 교육 데이터가 외부로 나가는 것을 꺼리는 경우가 있다. 이 시스템은 그런 상황에서도 사용할 수 있도록 다음 구조를 가진다.

| 설계 요소 | 의미 |
|---|---|
| 로컬 PDF 전처리 | 매뉴얼 PDF를 로컬에서 텍스트와 이미지로 분리 |
| 로컬 ChromaDB | 텍스트와 이미지 검색 인덱스를 PC 안에 저장 |
| 로컬 SigLIP | 이미지 판별과 텍스트-이미지 유사도 계산을 전처리 단계에서 수행 |
| 로컬 BGE-M3 | 질문, 텍스트, stage profile의 의미 유사도를 로컬에서 계산 |
| 로컬 Ollama LLM | Qwen/Gemma/Llama를 외부 API 없이 실행 |
| Streamlit 앱 | 브라우저에서 로컬 앱으로 질의응답 수행 |

또 하나의 목표는 8GB RAM급 제한 환경에서도 사용할 수 있는 구조를 만드는 것이다. 이를 위해 시스템은 런타임, 즉 사용자가 질문하는 순간에 필요한 메모리를 줄이도록 설계되어 있다.

1. SigLIP은 전처리 단계에서만 사용한다.  
   이미지 분류와 텍스트-이미지 similarity는 미리 계산해 저장한다. 앱 실행 중에는 SigLIP을 다시 로드하지 않는 방향이므로, 실시간 RAM 사용량을 줄일 수 있다.

2. 이미지는 벡터화된 검색 문서로 바꿔 저장한다.  
   앱은 매번 이미지 자체를 해석하는 것이 아니라, 이미지 주변 텍스트와 page 정보를 담은 image collection을 검색한다.

3. LLM은 Ollama의 양자화 모델을 사용한다.  
   Qwen 7B, Gemma 9B, Llama 8B 계열 모델을 원본 FP16 크기로 올리는 것이 아니라, Ollama에서 제공하는 4-bit 계열 양자화 모델로 실행한다. 이렇게 하면 모델 크기와 실행 메모리를 크게 줄일 수 있다.

4. 한 번에 하나의 LLM만 실행한다.  
   앱 파일은 `app_qwen.py`, `app_gemma.py`, `app_llama.py`로 나뉘어 있으며, 비교 실험이 아니라 실제 사용 시에는 하나의 모델만 선택해 실행하는 구조이다.

5. 검색 결과 수를 제한한다.  
   앱은 답변용 텍스트 Top-5와 이미지 Top-10을 중심으로 보여준다. 후보를 지나치게 많이 유지하지 않도록 하여 검색과 화면 표시 부담을 줄인다.

다만 현재 정량 평가는 개발용 노트북에서 수행된 결과이다. 따라서 논문에서는 “8GB RAM 환경에서도 완전히 검증되었다”고 쓰기보다는, “8GB RAM급 제한 환경을 목표로 오프라인·저사양 구동 구조를 설계했으며, 최소 사양 재현성 검증은 후속 실험 항목으로 남아 있다”고 쓰는 것이 정확하다.

## 7. 텍스트 전처리 방식

텍스트 전처리는 `src/text_filter.py`에서 수행한다. 목표는 PDF 전체를 아무렇게나 자르는 것이 아니라, 검색에 사용할 수 있는 의미 있는 텍스트 덩어리, 즉 chunk를 만드는 것이다.

### 7.1 물리적 청킹

먼저 PDF page에서 텍스트를 읽는다. 이때 단순히 글자만 가져오는 것이 아니라 다음 정보도 함께 저장한다.

- 텍스트 내용
- 해당 page 번호
- heading
- 텍스트 bbox 좌표

bbox는 PDF 안에서 텍스트가 어디에 위치하는지 나타내는 좌표이다. 이 좌표는 나중에 이미지와 텍스트가 가까운지 계산할 때 사용된다.

예를 들어 어떤 문장이 page 115의 왼쪽 위에 있고, 그림이 같은 page의 바로 아래에 있다면 두 자료는 관련 있을 가능성이 높다.

### 7.2 의미론적 청킹

물리적으로 모은 텍스트를 다시 문장 단위로 나누고, BGE-M3 임베딩을 이용해 문장 간 의미 유사도를 계산한다. 서로 의미가 가까운 문장들은 같은 chunk로 묶고, 주제가 바뀌면 새 chunk로 나눈다.

결과는 `data/processed/text_chunks.json`에 저장된다.

각 chunk는 대략 다음 구조를 가진다.

```json
{
  "heading": "로봇 베이스 고정하기",
  "text": "M8 볼트를 이용하여 고정하십시오...",
  "pages": [115],
  "bboxes": [...]
}
```

이렇게 만든 chunk가 이후 텍스트 검색의 기본 단위가 된다.

## 8. 이미지/도식 전처리 방식

이미지 전처리는 `src/unified_extractor.py`에서 수행한다. PDF에는 실제 도식뿐 아니라 로고, 아이콘, 빈 이미지, 장식 이미지도 들어 있을 수 있다. 따라서 단순히 모든 이미지를 저장하면 검색 품질이 떨어진다.

이미지 전처리는 다음 순서로 진행된다.

### 8.1 PDF에서 이미지 추출

PyMuPDF를 이용해 PDF page를 순회하면서 이미지 객체를 추출한다. 각 이미지에 대해 다음 정보를 기록한다.

- 파일명
- page 번호
- 이미지 bbox 좌표
- width, height
- 이미지 hash

### 8.2 큰 이미지를 잘라내기

매뉴얼에는 여러 도식이 하나의 큰 이미지로 묶여 있는 경우가 있다. 이런 경우 텍스트 위치를 절취선처럼 이용하여 이미지를 여러 조각으로 나눈다.

예를 들어 한 page에 위쪽 그림, 중간 설명, 아래쪽 그림이 하나의 이미지로 들어 있다면, 텍스트가 있는 위치를 기준으로 위쪽 그림과 아래쪽 그림을 분리한다.

### 8.3 불필요한 이미지 제거

다음 이미지는 제거한다.

- 완전히 비어 있거나 단색에 가까운 이미지
- 너무 자주 반복되는 로고성 이미지
- 너무 작고 정사각형에 가까운 아이콘

### 8.4 SigLIP으로 도식 여부 판별

남은 이미지에 대해 SigLIP을 사용한다. 여기서는 이미지가 실제 기술 도식인지, 빈 배경인지 구분한다.

사용한 label은 다음과 같은 의미이다.

- blank white page or empty background
- technical robot diagram or engineering schematic

기술 도식일 확률이 충분히 높은 이미지만 `data/processed/final_refined_data/`에 저장한다.

결과 메타데이터는 `data/processed/final_processing_report.json`에 저장된다.

## 9. 텍스트와 이미지를 연결하는 방식

이 시스템의 핵심은 텍스트와 이미지를 함께 검색하는 것이다. 이를 위해 전처리 단계에서 텍스트 chunk와 이미지 사이의 관련성을 계산한다.

텍스트와 이미지를 연결할 때 사용하는 신호는 크게 세 가지이다.

### 9.1 같은 page 또는 인접 page

매뉴얼에서 어떤 설명과 그림은 보통 같은 page에 있거나 바로 다음 page에 있다. 따라서 텍스트 chunk의 page와 이미지 page가 가까우면 관련성이 높다고 본다.

예를 들어 텍스트 chunk가 page 115에 있고 이미지도 page 115에 있으면 관련 가능성이 높다. 이미지가 page 116이면 여전히 관련 가능성이 있지만, 같은 page보다는 낮은 점수를 준다.

### 9.2 텍스트 bbox와 이미지 bbox의 거리

PDF 안에서 텍스트와 이미지의 좌표를 알고 있으므로, 두 객체의 중심점 사이 거리를 계산할 수 있다.

`src/embedding_text_image.py`의 `calculate_2d_distance`는 다음을 계산한다.

- 텍스트 bbox들의 중심점
- 이미지 bbox의 중심점
- 두 중심점 사이의 2차원 거리

거리가 가까울수록 텍스트와 이미지가 관련 있을 가능성이 높다. 또한 매뉴얼에서는 설명 텍스트 아래에 그림이 배치되는 경우가 많기 때문에, 이미지가 텍스트 아래쪽에 있으면 약간의 보정을 준다.

### 9.3 SigLIP image-text similarity

위치가 가깝다고 항상 관련 있는 것은 아니다. 그래서 SigLIP을 이용해 텍스트 내용과 이미지가 의미적으로도 맞는지 확인한다.

방법은 다음과 같다.

1. 텍스트 chunk의 heading과 본문을 합쳐 SigLIP용 text prompt를 만든다.
2. 이미지 feature를 SigLIP으로 미리 계산해 둔다.
3. 텍스트 feature와 이미지 feature의 유사도를 계산한다.
4. 그 결과를 `image_text_similarity`로 저장한다.

최종 매핑 점수는 거리 기반 점수와 SigLIP 유사도 점수를 합쳐 만든다.

```text
hybrid_score = 0.45 * distance_score + 0.55 * siglip_similarity
```

이 점수는 나중에 이미지 후보를 정렬할 때 `mapping_score`와 `siglip_score`로 사용된다.

## 10. 이미지 검색 collection은 어떻게 만드는가

이미지를 직접 벡터화해서 검색하는 것이 아니라, 현재 구조에서는 이미지와 관련된 설명 문서를 만든 뒤 그 문서를 BGE-M3로 임베딩한다.

`src/image_index.py`는 각 이미지에 대해 다음과 같은 문서를 만든다.

```text
image file: page_115_img_0_0.jpeg
manual page: 115
diagram confidence: 0.93
nearby text 1: chunk_..., heading 로봇 베이스 고정하기. M8 볼트를 이용하여...
nearby text 2: ...
```

이 문서는 이미지 자체가 아니라 “이 이미지가 어떤 page에 있고, 주변에 어떤 텍스트가 있었는지”를 설명하는 텍스트이다.

그 다음 이 문서를 BGE-M3로 임베딩하여 ChromaDB의 image collection에 저장한다.

따라서 사용자가 “로봇 베이스 고정 볼트”라고 질문하면, 이미지 collection에서도 “M8 볼트”, “로봇 베이스 고정하기”, “page 115” 같은 문맥을 가진 이미지 문서가 검색될 수 있다.

## 11. ChromaDB에는 무엇이 저장되는가

ChromaDB에는 크게 두 가지 collection이 있다.

| collection | 이름 | 내용 |
|---|---|---|
| 텍스트 collection | `doosan_manual_collection` | 매뉴얼 텍스트 chunk |
| 이미지 collection | `doosan_image_collection` | 이미지 파일과 주변 텍스트를 설명하는 이미지 문서 |

텍스트 collection에는 다음이 들어간다.

- chunk ID
- chunk 본문
- heading
- page
- linked_images
- mapping_candidates
- embedding

이미지 collection에는 다음이 들어간다.

- image ID
- 이미지 설명 문서
- file_name
- page
- image_path
- source_chunk_ids
- source_headings
- source_pages
- embedding

## 12. 사용자가 질문하면 일어나는 일

런타임 검색은 `src/rag_search.py`의 `retrieve_multimodal`에서 수행된다.

사용자가 질문을 입력하면 다음 순서로 처리된다.

### 12.1 질문 임베딩

질문을 BGE-M3로 임베딩한다.

```text
질문: "로봇 베이스를 바닥에 고정할 때 사용하는 볼트의 규격은?"
  -> BGE-M3
  -> query embedding
```

이 임베딩은 텍스트 collection과 이미지 collection을 검색하는 데 사용된다.

### 12.2 답변용 텍스트 검색

먼저 텍스트 collection에서 질문과 가장 의미가 가까운 텍스트 chunk를 찾는다. 앱에서는 기본적으로 Top-5 텍스트를 답변 근거로 사용한다.

이 Top-5 텍스트는 LLM에게 전달되는 context가 된다.

```text
[관련도 1순위 자료 | 출처: 로봇 베이스 고정하기]
M8 볼트를 이용하여 고정하십시오...

[관련도 2순위 자료 | 출처: ...]
...
```

### 12.3 이미지 후보 수집

이미지는 한 가지 방식으로만 찾지 않는다. 여러 경로에서 후보를 모은 뒤 점수를 합친다.

이미지 후보를 모으는 경로는 다음과 같다.

| 후보 경로 | 설명 |
|---|---|
| 텍스트에 직접 연결된 이미지 | 검색된 텍스트 chunk의 `linked_images`에 들어 있는 이미지 |
| page neighbor 이미지 | 검색된 텍스트 chunk와 같은 page 또는 인접 page의 이미지 |
| image collection 검색 | 질문 임베딩으로 이미지 collection을 검색해서 나온 이미지 |
| G4 stage map 이미지 | G4에서 실습 단계 page 범위에 포함되는 이미지 |
| G4 stage query 이미지 | 실습 단계명과 질문을 합친 질의로 image collection을 추가 검색한 이미지 |

이렇게 여러 경로에서 나온 이미지를 하나의 후보 목록으로 합친다.

## 13. G3에서 이미지 점수는 어떻게 계산되는가

G3는 멀티모달 RAG이다. G3의 목표는 텍스트 검색 결과와 이미지 검색 결과를 함께 이용해 관련 이미지를 찾는 것이다.

각 이미지 후보는 여러 점수를 가진다.

| 점수 | 의미 |
|---|---|
| `image_search_score` | image collection에서 질문과 얼마나 가까운지 |
| `text_rank_score` | 상위 텍스트 검색 결과와 연결되어 있는지 |
| `page_score` | 검색된 텍스트와 같은 page 또는 가까운 page에 있는지 |
| `mapping_score` | 전처리 단계의 텍스트-이미지 hybrid mapping 점수 |
| `siglip_score` | SigLIP 기반 이미지/도식 신뢰도 또는 image-text 신호 |
| `source_bonus` | 여러 경로에서 반복적으로 후보로 잡혔는지 |

G3의 기본 이미지 점수는 대략 다음과 같이 계산된다.

```text
base_score =
  0.42 * image_search_score
+ 0.18 * text_rank_score
+ 0.28 * page_score
+ 0.09 * mapping_score
+ 0.03 * siglip_score
+ source_bonus
```

이 공식의 의미는 다음과 같다.

- 이미지 collection 검색에서 잘 나온 이미지를 가장 중요하게 본다.
- 답변용 텍스트와 가까운 page에 있는 이미지도 중요하게 본다.
- 전처리 단계에서 텍스트와 이미지가 잘 매핑된 경우 추가 점수를 준다.
- SigLIP 신호는 보조적으로 사용한다.
- 여러 경로에서 동시에 잡힌 이미지는 조금 더 신뢰한다.

## 14. G4는 G3에서 무엇을 추가하는가

G4는 상황 인지형 멀티모달 RAG이다. 여기서 상황은 사용자의 실습 단계 또는 질문이 속한 매뉴얼 맥락을 뜻한다.

G3는 질문 자체와 이미지/텍스트의 유사도를 중심으로 검색한다. 하지만 협동 로봇 실습에서는 같은 단어가 여러 단계에서 반복될 수 있다. 예를 들어 “설정”, “전원”, “상태”, “I/O” 같은 단어는 여러 section에 등장한다.

G4는 질문이 어떤 실습 단계에 속하는지 먼저 추정하고, 그 단계와 관련된 page, section, keyword를 이용해 후보 순위를 다시 조정한다.

## 15. G4 실습 단계 추정

G4는 사용자가 직접 실습 단계를 선택하지 않아도 되도록 질문 기반 단계 추정기를 사용한다. 코드는 `src/stage_classifier.py`에 있다.

먼저 각 실습 단계에 대해 stage profile을 만든다. stage profile은 다음 정보를 합친 텍스트이다.

- stage ID
- 실습 단계명
- section keyword
- 본문 keyword
- 동작/질문 keyword
- 근거 문장

예를 들어 `설치/기구 고정` 단계의 profile에는 다음과 같은 표현이 들어갈 수 있다.

```text
설치/기구 고정, 로봇 베이스, M8, 볼트, 토크, 고정, 설치 page ...
```

질문이 들어오면 질문 임베딩과 모든 stage profile 임베딩의 cosine similarity를 계산한다.

```text
질문 embedding
  vs 설치/기구 고정 profile
  vs 안전/전원/접지 profile
  vs 티치 펜던트/USB 데이터 관리 profile
  ...
```

가장 높은 점수를 받은 단계가 예측 단계가 된다. 하지만 무조건 G4를 적용하지는 않는다. 다음 기준을 통과해야 한다.

| 기준 | 값 |
|---|---:|
| 최소 score | 0.45 |
| 1위와 2위의 최소 margin | 0.03 |

이 기준을 만족하면 G4를 적용한다. 기준을 만족하지 못하면 단계가 애매하다고 보고 G3 방식으로 fallback한다.

이 fallback은 중요하다. 애매한 단계로 잘못 re-ranking하면 오히려 검색 성능이 나빠질 수 있기 때문이다.

## 16. G4 context map

G4는 stage context map을 사용한다. 이 파일은 `SCIE용/data/11_stage_context_map_manual.csv`에 있다.

context map은 실습 단계별로 다음 정보를 담고 있다.

| 항목 | 의미 |
|---|---|
| 실습 단계 | 단계 이름 |
| 텍스트 페이지 범위 | 해당 단계의 설명 텍스트가 주로 있는 page |
| 이미지 페이지 범위 | 해당 단계의 이미지/도식이 주로 있는 page |
| 섹션 키워드 | 관련 section heading |
| 본문 키워드 | 해당 단계에서 중요한 용어 |
| 동작/질문 키워드 | 사용자가 물을 가능성이 높은 표현 |
| 가중치 | 해당 단계 context의 반영 강도 |
| 근거 | 왜 이 page/keyword를 선택했는지 |

중요한 점은 context map에 정답 이미지 파일명이나 정답 chunk ID를 넣지 않았다는 것이다. 즉, `Q31의 정답은 page_103_img_0_0.jpeg`처럼 정답을 직접 넣은 것이 아니다.

context map에는 “티치 펜던트/USB 데이터 관리 단계는 어떤 page와 keyword와 관련되는가” 같은 일반적인 매뉴얼 구조만 들어간다.

## 17. G4 re-ranking 방식

G4는 G3 후보를 만든 뒤, 실습 단계 context를 이용해 후보 순위를 다시 계산한다.

### 17.1 텍스트 후보 re-ranking

G4에서는 답변용 텍스트를 더 넓게 가져온 뒤, stage context와 맞는 텍스트를 위로 올린다.

사용하는 점수는 다음과 같다.

- 후보 텍스트 page가 stage의 텍스트 page 범위에 포함되는가?
- 후보 텍스트 heading 또는 본문에 stage keyword가 들어 있는가?
- 후보 텍스트 section이 stage section과 관련 있는가?

### 17.2 이미지 후보 re-ranking

이미지 후보도 비슷하게 보정한다.

사용하는 점수는 다음과 같다.

| 점수 | 설명 |
|---|---|
| `stage_page_score` | 이미지 page가 해당 stage의 이미지 page 범위와 맞는지 |
| `stage_keyword_score` | 이미지 주변 문맥이 stage keyword와 맞는지 |
| `stage_section_score` | 이미지 주변 heading이 관련 section과 맞는지 |
| `stage_query_score` | stage명 + 질문으로 이미지 collection을 다시 검색한 점수 |
| `stage_map_score` | page, keyword, section을 합친 stage map 점수 |

stage map 점수는 다음 비중으로 계산된다.

```text
stage_map_score =
  0.58 * page_score
+ 0.27 * keyword_score
+ 0.15 * section_score
```

최종 G4 이미지 점수는 G3 base score에 stage context 점수를 더한다.

```text
G4 image score =
  G3 base_score
+ 0.32 * stage_score * rank_factor
+ 0.25 * stage_page_score
```

즉 G4는 완전히 새로운 검색기가 아니라, G3가 찾은 후보를 실습 단계 맥락에 맞게 다시 정렬하는 구조이다.

## 18. 실제 앱에서는 어떻게 보이는가

앱은 Streamlit으로 실행된다. 모델별 진입점은 다음과 같다.

| 앱 파일 | LLM |
|---|---|
| `src/app_qwen.py` | Qwen 2.5 7B Q4 |
| `src/app_gemma.py` | Gemma 2 9B Q4 |
| `src/app_llama.py` | Llama 3.1 8B Q4 |

앱에서 사용자는 질문을 입력한다. 사이드바에서는 G4 실습 단계 모드를 선택할 수 있다.

| 모드 | 의미 |
|---|---|
| 단계 추정 | 질문에서 실습 단계를 추정하고 G4 적용 |
| 수동 선택 | 사용자가 실습 단계를 직접 선택 |
| G4 사용 안 함 | stage context 없이 G3 방식으로 검색 |

기본 논문 실험 기준은 단계 추정 기반 G4이다. 수동 선택은 확인용 또는 디버깅용에 가깝다.

앱 화면에는 다음이 표시된다.

1. 추정 실습 단계
2. 로컬 LLM 답변
3. 참조한 Top-5 매뉴얼 원문
4. 참조 도면 이미지 Top-10

## 19. LLM은 어떻게 답변을 만드는가

LLM은 전체 매뉴얼을 다 읽지 않는다. 검색된 Top-5 텍스트 chunk만 context로 받는다.

프롬프트는 다음 원칙을 가진다.

- 한국어로만 답변한다.
- 제공된 매뉴얼 context만 사용한다.
- 근거가 부족하면 부족하다고 말한다.
- 사실을 지어내지 않는다.

즉, 시스템은 LLM이 아무 지식이나 꺼내 답하게 두는 것이 아니라, 먼저 매뉴얼에서 관련 근거를 찾고 그 근거 안에서 답하도록 제한한다.

이미지는 LLM에게 직접 입력되지 않는다. 대신 앱 화면 오른쪽에 관련 이미지 후보로 표시된다. 사용자는 답변을 읽으면서 관련 도식을 함께 확인할 수 있다.

## 20. G1, G2, G3, G4 차이

실험에서는 네 가지 비교군을 사용한다.

| 비교군 | 이름 | 핵심 아이디어 |
|---|---|---|
| G1 | Keyword Search | 키워드 일치 기반 단순 검색 |
| G2 | Text-only RAG | BGE-M3로 텍스트만 검색 |
| G3 | Multimodal RAG | 텍스트와 이미지 후보를 함께 검색 |
| G4 | Context-aware Multimodal RAG | G3에 실습 단계 추정과 context re-ranking 추가 |

각 비교군이 사용하는 요소는 다음과 같다.

| 요소 | G1 | G2 | G3 | G4 |
|---|---:|---:|---:|---:|
| 키워드 검색 | O | - | - | - |
| BGE-M3 텍스트 검색 | - | O | O | O |
| 이미지 후보 검색 | - | - | O | O |
| page proximity | - | - | O | O |
| 텍스트-이미지 매핑 점수 | - | - | O | O |
| SigLIP 신호 | - | - | O | O |
| 실습 단계 추정 | - | - | - | O |
| context map re-ranking | - | - | - | O |
| 로컬 LLM 답변 생성 | - | O | O | O |

## 21. 평가 결과를 쉽게 해석하면

최종 검색 성능은 다음과 같다.

| 비교군 | Text R@1 | Text R@5 | Text R@10 | Text MRR | Image R@1 | Image R@5 | Image R@10 | Image MRR |
|---|---:|---:|---:|---:|---:|---:|---:|---:|
| G1 | 75.7% | 95.7% | 98.6% | 0.837 | - | - | - | - |
| G2 | 81.4% | 95.7% | 100.0% | 0.879 | - | - | - | - |
| G3 | 81.4% | 95.7% | 100.0% | 0.879 | 32.9% | 70.0% | 75.7% | 0.485 |
| G4 | 85.7% | 95.7% | 100.0% | 0.903 | 37.1% | 75.7% | 87.1% | 0.539 |

쉽게 해석하면 다음과 같다.

- 텍스트 검색은 이미 꽤 잘 된다.
- 이미지 검색은 텍스트 검색보다 훨씬 어렵다.
- G3는 이미지를 검색할 수 있게 만들었지만, 정답 이미지를 1위로 올리는 능력은 아직 부족하다.
- G4는 실습 단계 정보를 반영해서 정답 이미지가 Top-5 또는 Top-10 안에 들어올 확률을 높였다.

G4는 G3 대비 다음이 개선되었다.

| 지표 | G3 | G4 | 변화 |
|---|---:|---:|---:|
| Image Recall@5 | 70.0% | 75.7% | +5.7%p |
| Image Recall@10 | 75.7% | 87.1% | +11.4%p |
| Image MRR | 0.485 | 0.539 | +0.054 |

따라서 논문에서 가장 강하게 주장할 수 있는 부분은 다음이다.

> G4는 단계 추정 기반 context-aware re-ranking을 통해 G3 대비 이미지 검색 순위를 개선하였다.

## 22. 응답 품질 결과는 어떻게 해석해야 하는가

응답 품질은 검색 성능과 별도로 평가했다. 모델은 Qwen, Gemma, Llama를 비교했다.

최신 G4 응답 품질 결과는 다음과 같다.

| 모델 | 평균 점수 | O | △ | X |
|---|---:|---:|---:|---:|
| Qwen | 3.99 | 47 | 14 | 9 |
| Gemma | 3.59 | 27 | 31 | 12 |
| Llama | 3.62 | 31 | 26 | 13 |

Qwen이 가장 안정적이지만, G4가 응답 품질까지 크게 올렸다고 말하기는 어렵다. G4의 핵심은 이미지 검색 문제를 완전히 해결한 것이 아니라, 관련 이미지 후보의 Top-5/Top-10 포함률과 평균 순위를 개선한 것이다. 생성 답변 품질은 검색 결과뿐 아니라 LLM의 문장 생성 능력, prompt, 답변 길이, 안전 표현 여부에도 영향을 받는다.

따라서 논문에서는 다음처럼 쓰는 것이 안전하다.

> G4 improved retrieval performance while maintaining comparable response quality.

즉, G4는 검색을 개선했고, 응답 품질은 Qwen 기준으로 비슷한 수준을 유지했다고 해석한다.

추가로 rubric 기반 평가 결과 중 논문 해석에 영향을 줄 수 있는 G4 우선 검토 대상 54개는 연구자 수동 검토를 완료했다. 검토 결과는 O 13개, △ 6개, X 35개였다. 이 검토는 전체 630개 응답을 모두 사람이 재채점한 것이 아니라, G4 오류 및 애매 사례를 중심으로 한 보완 검토이다.

## 23. G4 개선 사례

G4가 잘 작동한 대표 사례는 다음과 같다.

| 질문 번호 | 내용 | G3 이미지 순위 | G4 이미지 순위 | 이유 |
|---|---|---:|---:|---|
| Q31 | 티치 펜던트 USB 포트 용도 | Top-10 밖 | 3위 | USB 데이터 관리 단계 context 반영 |
| Q23 | 로봇 시스템 시간 기능 확인 위치 | Top-10 밖 | 5위 | UI/시스템 정보 확인 단계 context 반영 |
| Q02 | 제어기 전원 공급 접지 조건 | Top-10 밖 | 5위 | 안전/전원/접지 단계 context 반영 |

이 사례들은 G4가 실습 단계 context를 이용해 정답 이미지를 위로 끌어올린 경우이다.

## 24. G4 실패 사례

G4가 여전히 실패한 사례도 있다.

| 질문 번호 | 내용 | 실패 원인 |
|---|---|---|
| Q10 | 관절 각도 확인 메뉴 | 단계는 맞았지만 세부 화면 이미지 단서 부족 |
| Q28 | 케이블 방수 부품 | 같은 page 내 유사 이미지 구분 실패 |
| Q15 | 과거 에러 로그 추출 메뉴 | 질문 기반 단계 추정이 애매해 G3 fallback |

이 실패 사례는 현재 시스템의 한계를 보여준다. G4는 page-level 또는 section-level context에는 효과적이지만, 같은 page 안의 여러 이미지 중 정확히 하나를 고르는 image-level discrimination은 아직 부족하다.

## 25. 이 시스템의 강점

현재 시스템의 강점은 다음과 같다.

1. 텍스트와 이미지를 모두 다루는 멀티모달 검색 구조를 갖고 있다.
2. 이미지와 텍스트를 단순히 따로 검색하지 않고, page, bbox, 주변 텍스트, SigLIP 신호를 이용해 연결한다.
3. G4에서는 질문의 실습 단계를 추정하여 상황 정보를 검색 순위에 반영한다.
4. 정답 이미지 파일명을 context map에 넣지 않았기 때문에, 정답을 직접 알려주는 방식이 아니다.
5. Qwen/Gemma/Llama를 모두 로컬 Ollama 모델로 실행할 수 있어 외부 API 없이 오프라인 질의응답이 가능하다.
6. SigLIP은 전처리 단계에서만 사용하고, 앱에서는 저장된 인덱스와 양자화 LLM을 사용하므로 저사양 구동 목표와 맞다.
7. 8GB RAM급 노트북까지 고려한 제한 자원형 구동을 목표로 두고, 한 번에 하나의 양자화 LLM만 실행하는 구조로 설계되어 있다.
8. G1/G2/G3/G4 비교군과 Recall@k, MRR, Both@k 지표가 정리되어 논문 실험 구조로 사용할 수 있다.

## 26. 이 시스템의 한계

현재 시스템의 한계는 다음과 같다.

1. LLM이 이미지를 직접 보고 답변하는 구조는 아니다.
2. 이미지는 주변 텍스트와 page 정보를 통해 검색되므로, 이미지 내부의 세부 내용 구분은 제한적이다.
3. 같은 page에 비슷한 이미지가 여러 개 있으면 정답 이미지를 정확히 고르기 어렵다.
4. 질문 기반 단계 추정이 틀리거나 애매하면 G4 효과가 줄어든다.
5. 응답 품질 평가는 전체 630개에 대해 rubric 기반 1차 평가를 수행했고, G4 우선 검토 대상 54개에 대해서는 연구자 수동 검토를 완료하였다.
6. 8GB RAM급 제한 환경을 목표로 설계했지만, 전체 정량 평가는 개발용 노트북에서 수행되었기 때문에 최소 사양 재현성 검증은 별도로 필요하다.

## 27. 논문에서 주장할 수 있는 내용

현재 결과로 논문에서 주장할 수 있는 내용은 다음이다.

1. 협동 로봇 실습 매뉴얼에서는 텍스트뿐 아니라 이미지/도식 검색이 중요하다.
2. 텍스트 기반 RAG는 텍스트 검색에는 강하지만 이미지 검색을 제공하지 못한다.
3. G3 멀티모달 RAG는 이미지 검색을 가능하게 하지만 정답 이미지를 상위에 배치하는 데 한계가 있다.
4. G4는 질문 기반 실습 단계 추정과 context map 기반 re-ranking을 통해 관련 이미지 후보의 Top-5/Top-10 포함률과 평균 순위를 개선한다.
5. 다만 Image Recall@1은 여전히 낮기 때문에, 현재 시스템은 정답 이미지를 항상 1순위로 찾는 완성형 이미지 검색기가 아니라 후보 순위를 보정하는 구조로 이해해야 한다.
6. G4는 검색 성능은 개선했지만, 응답 품질 개선은 LLM과 prompt 설계의 영향을 받으므로 별도 개선이 필요하다.
7. 제안 시스템은 클라우드 API에 의존하지 않고 로컬 LLM과 로컬 벡터 DB를 사용하므로, 인터넷 연결이 제한된 실습 교육 환경에 적용 가능성이 있다.
8. 무거운 멀티모달 처리를 전처리 단계로 분리하고 양자화 LLM을 사용하므로, 8GB RAM급 제한 환경을 목표로 한 경량화 설계 방향을 가진다.
9. rubric 기반 응답 품질 평가 결과는 G4 우선 검토 대상 54개에 대한 연구자 검토로 보완하였다.

## 27.1 개선 사례와 실패 사례가 필요한 이유

G4의 정량 성능표만 보면 Image Recall@5, Image Recall@10, Image MRR이 개선되었지만, 그 숫자만으로는 G4가 왜 좋아졌는지 설명하기 어렵다. 그래서 논문에는 개선 사례와 실패 사례를 함께 넣는 것이 좋다.

개선 사례는 G4의 작동 원리를 보여준다. 예를 들어 G3에서는 정답 이미지가 Top-10 밖에 있었지만, G4에서 질문을 적절한 실습 단계로 추정하고 그 단계의 page 범위, section heading, keyword를 반영하여 정답 이미지가 Top-5 안으로 올라온 경우가 있다. 이런 사례는 G4가 단순히 이미지를 더 많이 검색한 것이 아니라, 실습 단계 context를 이용해 관련 후보의 순위를 조정했다는 근거가 된다.

실패 사례는 G4의 한계를 보여준다. 같은 page 안에 유사 이미지가 여러 개 있거나, 질문의 실습 단계 추정이 애매하거나, 이미지 내부의 세부 단서를 구분해야 하는 경우에는 G4도 정답 이미지를 찾지 못할 수 있다. 이 실패 사례는 약점이지만, 동시에 향후 image caption, bbox 주변 텍스트, 이미지 순서 정보, 세부 단계 라벨이 왜 필요한지를 설명하는 근거가 된다.

따라서 사례 분석의 역할은 다음과 같다.

| 사례 종류 | 역할 |
|---|---|
| 개선 사례 | G4가 실습 단계 context를 이용해 이미지 후보 순위를 어떻게 끌어올렸는지 설명 |
| 실패 사례 | G4가 아직 해결하지 못한 image-level distinction과 단계 추정 오류를 설명 |
| 둘 다 포함 | 성과를 과장하지 않으면서도 G4의 기여와 한계를 균형 있게 제시 |

과장하면 안 되는 내용은 다음이다.

- G4가 모든 질문에서 좋아졌다고 하면 안 된다.
- G4가 이미지 검색 문제를 완전히 해결했다고 하면 안 된다.
- LLM이 이미지를 직접 이해한다고 쓰면 안 된다.
- 전체 630개 응답을 전문가가 모두 재채점했다고 쓰면 안 된다.
- 8GB RAM급 환경에서 전체 실험을 검증했다고 쓰면 안 된다. 현재는 최소 사양 목표와 설계 방향으로 표현해야 한다.

## 28. 처음 보는 사람을 위한 짧은 예시

질문:

```text
티치 펜던트에 위치한 USB 포트의 주된 용도는 무엇입니까?
```

시스템 처리:

1. 질문을 BGE-M3로 임베딩한다.
2. 텍스트 collection에서 USB 포트와 관련된 설명을 찾는다.
3. image collection에서 USB, pendant, data import/export 주변 문맥을 가진 이미지를 찾는다.
4. G4가 질문을 `티치 펜던트/USB 데이터 관리` 단계로 추정한다.
5. 해당 단계의 page 범위와 keyword를 이용해 이미지 후보를 다시 정렬한다.
6. 정답 이미지 `page_103_img_0_0.jpeg`가 G4에서 3위로 올라온다.
7. 앱은 답변과 함께 해당 이미지를 보여준다.

이 예시는 G4가 왜 필요한지 잘 보여준다. 단순히 질문과 이미지 문서의 유사도만 보는 것이 아니라, “이 질문은 티치 펜던트 USB 데이터 관리 단계에 속한다”는 실습 맥락을 함께 반영했기 때문이다.

## 30. 한 장 요약

이 시스템은 협동 로봇 실습 매뉴얼을 텍스트와 이미지로 나누어 전처리하고, 각 텍스트와 이미지가 어떤 page와 위치에서 연결되는지 계산한 뒤, BGE-M3와 ChromaDB를 이용해 검색할 수 있도록 만든다. 이미지는 단순 파일로만 저장되는 것이 아니라, 주변 텍스트와 page 정보를 가진 검색 문서로 변환되어 image collection에 저장된다. 사용자가 질문하면 시스템은 관련 텍스트 Top-5와 이미지 Top-10을 검색하고, G4에서는 질문의 실습 단계를 추정해 해당 단계의 page, section, keyword context를 이용해 후보 순위를 재조정한다. 로컬 LLM은 검색된 텍스트 근거를 바탕으로 한국어 답변을 생성하고, 앱은 관련 이미지를 함께 보여준다. 전체 구조는 외부 API 없이 로컬에서 동작하도록 설계되었고, SigLIP 등 무거운 처리는 전처리 단계로 분리하며 양자화 LLM을 사용해 8GB RAM급 제한 환경을 목표로 한다.

따라서 본 시스템의 핵심은 단순 챗봇 구현이 아니라, 협동 로봇 실습 매뉴얼에서 텍스트, 이미지, 실습 단계 정보를 연결해 검색 성능을 높이는 context-aware multimodal RAG framework를 구현하고 평가한 것이다.
